The user approved these M2 design policies on 2026-10-22, resolving values the
assignment does not fix: angular speed cap 1 rad/s; future stamp tolerance 0 s;
crossing lease/renewal timeout 1 s; measured stop means exactly zero simulated
velocity. Car motion and traffic capacity/headway remain deferred to M4. These
are implementation choices, not newly discovered assignment requirements.

Other explicit baseline choices: fixed physics step 0.05 s (20 Hz); queue confidence
minimum 0.5; a 0.2 m upstream crossing ownership margin; local estop, measured door, crossing and supervisor heartbeat watchdogs
0.5 s; zero positional drift from graph centerlines beyond numerical tolerance
1e-6 m. Moving turns are rejected if their translation leaves a permitted edge;
controllers must turn while stopped at graph nodes. Queue confidence and all
speed/timeout parameters are range checked at startup. Safety limits may be
reduced, never raised beyond the assignment caps.

## Runtime boundary

`ros2 launch smart_hub_bringup m2.launch.py` starts four processes:

- `scenario_runner`: fixed-step world, final-command adapters, camera (10 Hz,
  sensor QoS), noisy `/hub/vehicles` (10 Hz), slot observations (5 Hz), robot and bus odometry
  (20 Hz), both TF chains, and measured door/barrier status heartbeats (10 Hz).
- `safety_supervisor`: candidate validation and final commands (20 Hz), safety
  heartbeat (10 Hz), stop latch, deliberate clear, reset hold, and transition events.
- `hub_coordinator`: crossing service and state (10 Hz), FIFO waiting requesters,
  token ownership, 1 s renewal lease and 2 s continuous-clear debounce.
- `reset_coordinator`: bounded asynchronous public reset; one total 1 s deadline,
  no automatic retries, busy/unavailable/denied/timeout outcomes.

The launch deliberately requires an external fresh `/hub/queue` observation and
operator `/hub/estop` heartbeat. Without them it stays stopped with UNKNOWN
crossing. M2 has no perception or mission controllers: the verification probe
supplies clearly labelled synthetic observations and candidate commands. A
candidate is not a mission goal; goal lifecycle/abort/cancel behavior starts in
M3/M6. Clearing the latch discards old candidates and requires a newly stamped
candidate; later mission controllers must require a new goal after stop.

There is no `/clock` publisher. All nodes use wall-backed ROS time for acquisition
stamps and monotonic time for receipt ages, leases and latency. Do not enable
`use_sim_time` independently. The physics RNG and observation RNG are separate;
pose noise is bounded uniform per axis at ±0.02 m and yaw at ±0.01 rad
(synthetic design choices). Crossing clearance inflates observed footprints by
the known maximum position error, sqrt(2) × 0.02 m, plus maximum travel
since acquisition before proving empty. Lease loss starts a new clear debounce. The
simulator independently inhibits entry while another physical footprint occupies C.
`/sim/evaluator/ground_truth` is a 10 Hz `VehicleStateArray` solely for evaluators;
control nodes never subscribe to it. The simulator's physics/interlocks necessarily
use its internal physical state. Camera images are synthetic scene drawings,
not detection results or real-video evidence.

Only the baseline bus/robot and empty parking observations run in M2. Runtime
`obstacle_enabled=true` is rejected because the M2 supervisor has no obstacle
observation contract yet; the pure world collision test exercises O separately.
Obstacle observations, traffic decisions and mission progress are later gates.
The barrier stays closed because no M2 parking owner can authorize opening. A
bus door request opens only at B, stopped, within docking tolerances; propulsion
is independently inhibited while measured open. Door dwell belongs to M3.

## Crossing and reset protocol

Crossing decisions use fresh queue and vehicle observations, including full agent
radii. Missing/invalid/future/frozen input is UNKNOWN, never clear. Lost renewal
produces HOLD with retained owner; no competitor can acquire an occupied crossing.
The same retained owner can renew its matching token after fresh pedestrian-free
observations, restoring OWNED so it can exit. Expired ownership is removed only
after observed full clearance and debounce. RELEASE cannot override occupancy.

Safety accepts only the M2 bus/robot vehicle set; extra agents remain UNKNOWN until
M4 extends collision prediction.

The public `/scenario/reset` supports only `m2_baseline`. It rejects unknown
scenarios, asserted/latching stop, stale inputs, hazards, nonzero motion and busy
resets. Internal services use the existing `ResetScenario` schema; they add no
public interface definitions:

1. `/safety/reset_state` validates safe feedback, flushes candidates and enters a
   zero-output hold. The coordinator observes the safety hold heartbeat.
2. `/crossing/reset_state` clears administrative ownership only after fresh physical
   clearance, then publishes state. The coordinator observes a new CLEAR sample.
3. `/sim/reset_world` requires fresh supervisor hold, clear crossing and measured
   zero; restores the seed, world and observation RNG; flushes actuator commands;
   returns a new run ID.
4. `/safety/finish_reset` revalidates safe feedback, discards candidates again and
   releases hold. Candidate stamps at/before completion remain rejected.

Success means every participant acknowledged. Partial failure returns failure,
never claims rollback, and intentionally leaves the supervisor holding zero.
Restore safe inputs/participants and explicitly retry reset. M2 has no active
mission actions to cancel; future participants must extend this handshake before
being launched with reset. `preserve_logs` does not delete evidence in either mode;
external verification owns immutable run records.

The asynchronous client/callback design follows the official
[Jazzy callback group guidance](https://docs.ros.org/en/jazzy/How-To-Guides/Using-callback-groups.html).
The coordinator uses a single-threaded executor, reentrant asynchronous callbacks,
a busy guard, and a timer deadline; it never blocks with synchronous service calls.

## Reproduction and status

Run as the ordinary user on the existing Ubuntu host using the Ubuntu 24.04 Jazzy
container; do not install Jazzy onto the Ubuntu 22.04 host or change permissions.

```bash
docker build -t smh-m2 -f containers/Dockerfile .
docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp \
  -v "$PWD:/workspace" smh-m2 \
  bash scripts/m2_container.sh /workspace/evidence/runs/UNIQUE_M2_RUN_ID
```

The destination must not already exist. The script copies source to a clean
workspace; records OS, Python, ROS, packages, commit, dirty state and file hashes;
runs M1 contract/interface regression, lint, colcon build/test/results; then runs
the real-process harness. `acceptance.json` records individual status and observed
values. CI retains this evidence as an artifact even on failure.
